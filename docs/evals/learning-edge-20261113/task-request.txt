三、深化局部纠错，避免正确工作反复重做

已有DAG和“只重派失败项”协议，优先补实际缺口，不重造图执行平台。

   使用现有graph表达，只有明确无法表达且有反例时才做最小兼容扩展。

2. 将可复用单元的验收证据绑定到相关输入、输出、接口、检查器和策略版本。
   输入或接口改变时，使受影响的下游结果失效；
   仅修改失败单元时，保留不受影响的已接受单元。

3. 失败返回应包含具体失败证据、允许修改的范围、仍需满足的条件和重试依据。
   重试要改变相关条件；累计失败不能靠换task名或策略标签清零。

4. 用生产入口证明：
   多个单元中一个失败时，不会重新派发并改写其他正确单元；
   上游输入改变时，不会错误复用下游旧PASS。
   最终集成Gate仍须按契约执行。

四、把学习接到拆分和派工的真实消费路径

现有Python工具策略进化继续保留。本次补的是宿主执行循环中的策略消费。

1. 从真实失败或开销轨迹形成有适用范围的候选约束。
   候选至少包含：来源证据、可复现问题、行为差异、适用条件、
   预期收益、反证条件、版本和撤回条件。

2. 学习结果应影响控制器怎样拆分任务、选择串行或并行、组织上下文、
   安排检查或选择已有工具。不要只追加worker指令、写复盘或打印建议。

3. 派工前实际读取符合条件的已启用策略，生成计划/brief，并记录：
   消费了哪个版本、匹配什么条件、因此改变了什么。
   不适用时沿用基线；候选未通过验证时不得偷偷生效。
   学到的经验不能扩大权限、放松Gate或改变冻结契约。

4. 复用现有候选、留出验证、晋升、恢复与撤回机制。
   需要扩展时保持同一统计预算与失败历史，不另建策略平台。
   确定性变换用本地代码；需要判断和候选生成时使用宿主原生能力。

5. 验证候选→验证→启用/保留→下一任务消费→退化撤回的完整生产路径。
   同时覆盖：开发集获益但留出退化、不适用规则误匹配、
   策略版本变化、切换中断和撤回后误用旧规则。

6. 合格候选不一定存在。拒绝晋升可以是正确结果。
   用受控数据验证机制时明确标注；不能把机制测试当成真实效用证明，
   也不能为完成任务而降低晋升门槛。
