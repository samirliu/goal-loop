# 直接提交：减少默认地图工作流中的机械往返

本轮从 `00e68c2` 开始，候选位于 `perf/direct-submit-20261113`。主分支保留上一轮基线。本轮实现了实质的协议减负，**尚未证明新版本在真实复杂任务上的净交付收益**；上一轮 18 个位置的失败、成本和未采用决定全部保持原样。

## 改动

1. `goal_host.py begin/enter … --context` 在原宿主绑定和最早预算建立后直接返回地图，省去单独取图。身份仍须来自唯一真实回执或显式实际身份；不猜 session，不续预算。
2. `submissions.stamp.command` 在原锁和截止内运行冒烟，然后调用原 stamp。初始业务 FAIL 是修复任务的正常起点；BROKEN、超时、变更树或账本、不完整检查不能盖戳。手动/auto 批准标记继续沿用原规则。
3. `submissions.close.command` 接收实际判断 JSON。先核对用户观察到的 revision，再推导 operation_id、单任务范围、符合条件的检查数和 claim 终验，保存原标准 proposal，最后同 PID 交给原 controller。模型不用先写 proposal、重取地图，再执行 close。
4. 地图直接显示验收条款，并绑定 scripts/ 中全部 Python、Bash、awk 文件。契约、产物、计划、证据、输入、crew、策略、预算和实现版本变化时继续拒绝旧请求。
5. 默认 SKILL 与实际程序合并路径保持一致。普通任务不再需要填写优化策略表、手动维护 operation_id、重复运行程序已负责的收尾步骤或在终报中倾倒协议字段；crew/优化/判断/外部事实只按对应能力加载，五条不变量和原检查继续保留。

确定性单任务常见提交只包含：

```json
{
  "progress": "yes",
  "exit_signal": "yes",
  "adversarial": "clear",
  "adversarial_note": "已经实际执行的复审命令、结果和观察"
}
```

必须先进行真实复审，不能照抄示例制造 clear。`progress=no` 仍须给实际 `strategy_delta`；特殊契约仍要求真实的计数、score、strategy、dry 等字段。自动模式不支持的观测没有被猜成零或 PASS。

原 `actions`、文件请求和直接 CLI 保持兼容。pending 时继续走原 recover；提交前中断恢复保存的请求，提交后中断沿用原 argv 重放，不重复记账。历史 REPLAY 后仍执行当前原 audit/Gate，不发历史 GO。

## 本地机制对照

[measure_protocol.py](measure_protocol.py) 在每次执行前写出源码哈希与固定顺序，使用新临时项目比较“原推荐地图/文件流程”与“直接提交流程”，各三次。两边同样从失败的业务检查开始、实际修复、实际复审，最后通过原 audit/Gate，并只记录一次迭代。

| 指标 | 原地图/文件流程 | 直接提交 |
| --- | ---: | ---: |
| 外部协议 CLI 调用 | 12 | 5 |
| 模型提交字段 | 10 | 4 |
| 模型手写中间 proposal 文件 | 1 | 0 |
| 原 audit/Gate 最终通过 | 3/3 | 3/3 |

调用减少 58.3%，字段减少 60%。具体过程时间与完整原输出在 [mechanism-summary.json](mechanism-summary.json)、[mechanism-results.json](mechanism-results.json)。本机首版均值约 7.45→5.20 秒；最终源码版本的测量以无 v1 后缀的文件为准。v1 与其源码身份仍保留。

这只是无模型的本地生命周期诊断。旧底层命令本来可以手动批处理，因此 12→5 不是所有宿主调用的理论下界；CLI 数量也不等于模型轮数。这里没有真实复杂任务、模型 token 或账单测量，不能据此宣称复杂任务节省 30% 或建立回本。

## 回归和反例

- 修改前真实 CLI 不支持 `submit`，完整生命周期反例失败，见 [before-submit.log](before-submit.log)。
- 新回归覆盖：一次提交完成原收账与终验；旧产物/契约/计划/proposal 拒绝；缺复审拒绝；派生控制字段不可覆盖；实际业务失败与假完成计数保留；原继承预算不延长；提交前/后中断与精确重放；正常失败初始条件、损坏或变更型检查器；宿主最早起点和手动批准标记；数值契约显式观测；入口域错误保持原错误路径。
- 原地图 19 项、原机械收尾 9 项、宿主预算 11 项通过，日志分别为 `context-compatibility.log`、`measured-close-compatibility.log`、`host-budget-compatibility.log`。新增 21 项完整回归通过，另一个入口错误回归单独通过；完整 CI 汇总还会验证全部测试。
- 首次开发测试对 prompt scope 名称、手动 stamp 标记和 mutation 返回码有错误假设，记录保留。开发还修正了必须允许“初始业务 FAIL”盖戳，以及数值测试的 expected 字段位置；没有改旧断言、增加旧超时或跳过失败。

## 真实交付验证与采用决定

旧的六个留出任务已经曝光，不作为新收益证明。上一轮 18 次真实评测额度已用完。本轮新增真实模型位置目前为 0，新的预算选项已经提交用户，尚未得到额度答复。

要证明真实收益，需要先冻结当前候选，再采用新的复杂任务、独立验收器、全新上下文和一致预算，对照裸宿主与冻结基线。调用/字段减少只作诊断，采用仍看完整交付率和含全部失败的单位交付成本；不补跑旧失败或改旧分母。

因此本轮当前决定是：候选独立分支供审查和完整 CI 验证；主分支保留基线，暂不宣称净提效或回本。研究、实现、无模型机制测量和后续真实模型验证须分开记成本，未知费用不按零计。完整 CI 的同提交回执保存于本目录的 `verification-final/`，不会递归提交进它验证的同一提交。

`974d6ac` 的中间 CI 因默认说明仍重复要求模型做程序已经完成的工作而取消，完整日志、取消理由和成本记录保留在 `verification-obsolete-974d6ac/`，不记为通过。最终默认 SKILL 从基线 124 行、6,435 字符收敛为 69 行、3,759 字符；大小仅作诊断，实质变化是取消重复义务和按能力加载规则，见 [workflow-compaction.json](workflow-compaction.json)。五条不变量、旧断言、旧超时和所有原执行入口均保留。最终提交重新跑完整双平台 CI。
