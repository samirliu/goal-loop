# goal-loop 深化优化方案

日期：2026-11-04  
评审基线：v4.1.1，提交 `7bf9669f0c425399121f03db2427aa69a5a6ce54`  
文档状态：实施方案；本文件中的新增机制、字段和测试均为待实施项，除非明确标注已存在。

## 1. 要达到的结果

把 goal-loop 从“具有验收纪律的执行流程”推进到“证据可信、预算可控、能验证策略改进的智能体循环”。

用户的原始目标是：正确的 Agentic Loop、支持自主优化的 evals 与 metrics、适当使用 crew subagent，并通过循环持续进化。对此采用三个可分别验证的结果：

1. **交付可信**：GO 对应可重现的实际产物和有效证据；变化、错误、恢复不会复用失效结论。
2. **执行有效**：在相同总预算下，获得更高的有效交付率或更好的交付质量；并行净收益可测。
3. **学习有效**：策略能从失败中形成候选，在未参与调优的任务上验证，获益不足时撤回。

这三项不能互相代替。门控正确不等于任务解决能力更强；分数上升不等于策略有效；本任务成功不等于跨任务迁移。

### 1.1 深化边界

- 保留 GATE、BIND、PROVE、GRADIENT、FENCE 五条不变量；新增行为应说明归属，不再增加常驻法律。
- 不以增加角色、模式、旗标、文档长度或测试数量作为成果。
- 先修共享底层语义，再修改协议表述；避免让 agent 靠记忆补偿脚本缺陷。
- 保持入口按需加载；复杂恢复和实验细节放到已有 references 或实现中。
- 不整体重写语言或引入大型评估框架。新增依赖必须对应已证实的实现需要，并说明安装与迁移成本。
- 学习过程中保持用户成功定义和验收器冻结；经授权的策略试验不需要每轮重新索要同一授权。

## 3. W1：基于实际内容绑定产物

### 3.1 当前缺陷

[goal_gate.sh](../scripts/goal_gate.sh) 的 Git 分支使用 `HEAD + git status --porcelain` 生成指纹。文件连续处于 `M` 状态时，其实际内容再次改变，状态文本可以完全不变。

已复现：同一个 tracked 文件从原始内容改为 A，再改为 B，两次 dirty 状态都是 ` M artifact.txt`，得到相同 digest。

这既影响 judged 裁决过期判断，也影响检查器是否修改了已脏产物的检测。确定性检查仍会重跑，但证据绑定的保证不足。

### 3.2 实现方案

1. 在共享解析/工具层定义唯一的“受审产物清单与内容摘要”实现，gate、ctl、audit 不各写一套。
2. Git 用于发现受审路径和仓库边界，不把 status 文本当作内容证明。
3. 对清单中的每一项编码路径、文件类型、按契约有意义的权限及内容摘要；最终做稳定排序和聚合。
4. 明确新增、删除、重命名、符号链接、空文件、未跟踪文件和含特殊字符路径的语义。
5. Git 项目与非 Git 项目使用一致的内容语义；排除项的差异必须有理由。
6. 正常 ledger/evidence 写入不属于产物变化。被验收的生成产物即使被 `.gitignore` 忽略，也必须通过显式受审清单或独立 artifact hash 进入绑定。
7. 默认不跟随符号链接遍历任意树外路径；记录链接本身，确需绑定外部目标时由明确的验收范围指定。
8. 文件枚举、读取或哈希失败时返回状态错误，不把部分清单当作完整指纹。

建议使用带版本的内容摘要表示。具体算法与表示长度在实现时集中确定；保留路径分隔与字段编码的无歧义性，比简单更换哈希算法更优先。

### 3.3 兼容与迁移

- 旧摘要与新摘要不得无标记混用。
- 升级后保留历史证据，但旧算法产生的当前有效裁决必须重新绑定或重新测量。
- 不修改已批准的业务 AC 来迁就新指纹，也不把迁移错误计入假完成次数。
- 子目录运行只绑定声明的项目范围；不得无意纳入整个父仓库。
- 回退实现时不得把新格式强制解释成旧格式有效声明。

### 3.4 验收矩阵

| 用例 | 预期 |
|---|---|
| 同一个脏文件 A → B，Git status 不变 | digest 改变 |
| 未跟踪目录中同一路径内容变化 | digest 改变 |
| tracked 文件暂存后继续修改 | digest 反映实际交付内容 |
| 文件新增、删除、重命名 | digest 按受审范围改变 |
| 符号链接目标文本改变 | digest 改变，不擅自遍历目标 |
| 空格、换行等合法文件名 | 不漏项、不合并为同一条目 |
| 写入合法 evidence | 产物 digest 保持不变 |
| 被忽略但被验收的构建产物改变 | 对应绑定失效 |
| 检查器修改一个已经是 M 的文件 | 拒绝并报告 check-mutated-tree |
| 源码变化后复用旧 judged PASS | 拒绝旧裁决 |
| 读取清单中的文件失败 | 明确状态错误，不能 GO |

必须在真实 Git fixture 中测试，不能全部使用非 Git 临时目录。

## 4. W2：收账校验、提交与恢复一致

### 4.1 当前缺陷

[goal_ctl.sh](../scripts/goal_ctl.sh) 先写 `scores.rec`、`loop-log.md`、`state.rec`，后校验 `--adversarial`。

已复现：传入非法复审值，返回 `rc=4`，但 `iteration=1` 且新增了一轮账本。这是被拒绝的请求留下已提交效果，不是正常的“执行失败应当入账”。

### 4.2 第一阶段：完整预检

先把所有可在执行前确定的参数、枚举、必填关系、路径格式和策略约束移到首次状态写入之前。

目标顺序：

```text
解析与完整校验 → 测量 → 准备本轮记录 → 提交 → 门控验收
```

区分三种失败：

| 类型 | 是否形成已提交尝试 | 后续行为 |
|---|---|---|
| 参数或协议形状非法 | 否 | rc=4，持久状态不变 |
| 合法执行后的产品/测量失败 | 是 | 保留失败证据，按门控继续修复 |
| 提交中断 | 取决于明确提交点 | 恢复为一个完整版本，禁止半轮可见 |

测量命令仍应保持契约规定的只读产物语义；执行前预检不能替代测量前后的变化检测。

### 4.3 第二阶段：确定唯一提交点

不能把连续多个文件 `mv` 称作跨文件原子事务。

建议在保留现有文本视图的前提下，增加一份最小、可校验的权威提交记录：事件身份、本轮编号、关联证据、预期视图版本及完整性信息。现有 state/log/scores 是它的可恢复视图。

- 所有 writer 串行提交，使用原子获得的单写者锁；当前“先检查文件再覆盖”不足以提供原子互斥。
- 提交记录必须能识别尾部截断、重复提交和未知格式。
- 读取方先确认视图与提交版本一致；不一致时报告待恢复，不能拼接旧 state 与新 log 发 GO。
- controller 执行恢复；gate 不负责悄悄修账。
- 同一个提交身份重试时只产生一次效果；不能靠增加 iteration 绕过幂等性。
- 恢复只重建账本，不重新执行之前可能已经发生的外部工具副作用。

落地时先完成预检修复，再确定最小持久化实现。不要为了设计通用事件平台引入数据库服务或重做任务系统。

### 4.4 验收

- 所有非法参数拒绝前后，对持久 ledger 做内容比较，应完全一致。
- 在“测量完成、提交前、提交过程中、提交后更新视图”分别注入故障。
- 恢复后 iteration、scores、loop-log 和原始证据引用对应同一次提交。
- 相同提交重试不会重复加分、增加假完成次数或消耗两次迭代。
- 两个 controller 同时启动，只有一个成为 writer；被拒进程不删锁。
- 恢复前的只读 gate/status 不会把不一致视图报告为 GO。

## 5. W3：统一预算与进程生命周期

### 5.1 当前风险

[goal_loop.sh](../scripts/goal_loop.sh) 对每次模型调用重新执行 `timeout "$wallclock"`，外层没有独立的整场总截止判断；没有可用 timeout 时直接启动执行器。盖戳时预算又从当前时间计算，调用者需要自行扣除此前的规划时间。

当前修复的是执行目录和锁清理，不能据此宣称总预算、进程取消和原子锁已经完备。

### 5.2 目标语义

- 一个 run 只有一个总截止时间；规划、读取、排队、worker 启动、执行、join、重试和验收均在其中。
- harness 已提供开始/截止时间时沿用；只能观测到脚本入口时间时明确标为脚本观测预算，不能声称已覆盖更早的模型思考。
- 现有 `--wallclock` / `--time-budget` 保留为输入兼容层，内部解析成统一 deadline。
- 多个已有约束同时存在时使用最早截止；resume 不隐式延长。
- 每次启动和重试前计算剩余预算，执行器获得的超时不超过剩余预算。
- 为收账和最终检查预留有限预算；时间不足时停止扩任务，保留当前最佳结果与续写接口。
- 总预算耗尽后可以进行有界的结果结算，但不得继续不受限的搜索。
- 产品门控允许的“迟到但验证通过”与评估中的“预算内成功”分开记录。晚完成的 GO 不能回填为按时成功。

### 5.3 执行与取消

超时应传播到所属 worker/执行器，等待其有界退出，防止 controller 已结束但子进程继续改文件。只取消本 run 所拥有的进程；不得靠宽泛进程名匹配。

不能假定所有机器都有 GNU timeout。应提供明确、可测的替代实现，或在要求硬预算的场景拒绝无约束执行。计时采用同进程单调时钟衡量时长，持久化截止需另外处理重启与时钟异常，不把时钟回拨当作新预算。

### 5.4 验收

- 连续多轮的累计执行不能每轮获得完整初始预算。
- 慢启动、重试等待、检查超时和最终 sleep 都消耗同一预算。
- 没有 timeout 的环境仍有约束，或明确拒绝启动；不能静默失去限制。
- resume 后 deadline 不变；重复启动、只读检查不破坏现有 run。
- 超时后没有所属 worker 继续修改产物。
- 超时后的结算有上限，报告区分预算内成功、迟到通过和未完成。

## 6. W4：分离实际工作与声明次数

### 6.1 事件语义

保留兼容的 iteration 编号，但新增统计必须从事件含义派生，不直接把 block 数当作工作量。

| 事件 | 记录重点 | 用途 |
|---|---|---|
| 产物尝试 | 基线/候选摘要、策略、修改范围 | 实际搜索次数与归因 |
| 测量 | 输入、仪器版本、结果、耗时、波动 | 可比较性与成本 |
| 验收声明 | 当前产物、证据集合、GO/拒绝原因 | 假完成与协议摩擦 |
| 恢复 | 故障类别、受影响尝试、恢复动作 | 重试成本与可靠性 |

只补齐一份证据或重发声明，不自动记为产物改进。纯格式修正不应重置优化停滞计数；有效的新反例、必要的新测量也不能被一概视为无进展。

### 6.2 进度与重复验证

- 区分产物进度、信息增益和协议维护，避免统一依赖 `progress=yes` 自报。
- 在同一个产物摘要、契约版本、检查器版本和输入范围下，避免无理由重复昂贵准备工作。
- 证据缓存必须注明有效范围。外部事实、带随机性的检查、噪声估计与最终验收不能因缓存而省略必要重测。
- 保留现有门控确定性重跑；先减少重复声明和准备，不以“提效”为由削弱最终验收。

### 6.3 验收

复放现有三轮日志，应得到“一次实现尝试、相应测量、两次声明”，而不是三次优化。同一产物反复声明不会产生策略收益，也不会伪造进展。

## 7. W5：按净收益选择 crew

### 7.1 最小遥测

每个 worker 至少记录派发、首次有效产出、完成或故障时间，以及修改范围、结果是否被采用。每波记录 join、冲突修复、重复验证和 controller 协调耗时。

只在工具实际提供时记录 tokens/费用；缺失数据是 unknown，不是零。不采集内部思维链，工具调用与输出、产物和简要行动依据已足够用于此评估。

### 7.2 决策模型

```text
T_serial   ≈ Σ 子任务执行时间 + 验收
T_parallel ≈ 启动 + max(子任务执行时间) + 协调 + join + 返工 + 验收
```

在实际依赖图上比较关键路径。预测收益应足以覆盖估计误差；没有启动成本数据的短预算小任务保留串行默认。分数不能同时把更宽的 crew 当作免费资源。

排队时间计入用户等待时间，同时单独记录以分析资源争用。取消无产出的 worker 也有成本，应计入失败尝试。

### 7.3 验收

- 同一任务分别提供低/高启动延迟，策略选择能据证据发生变化。
- 多文件但高度耦合的任务，不因文件数量自动扩 worker。
- 确实独立、工时足够的任务，能在同等预算下体现并行净收益。
- 一个 worker 掉线后，已完成结果得到保留，恢复动作有界且入账。
- 对比同时报告总成本、交付时间和质量，不能只展示最快的成功轮次。

## 8. W6：从局部分差到候选策略验证

### 8.1 保留现有轻量反馈

[goal_strategy.awk](../scripts/goal_strategy.awk) 已正确处理进入首波收益、缺失读数断链、最新窗口覆盖和噪声信息不足。继续把 STRATEGY-PICK 作为当前任务的行动线索；不要把它解释为因果结论。

严格验证主要发生在候选晋升或昂贵决策时，不给每一轮都增加多模型评审。

### 8.2 候选比较流程

1. 保存可恢复的 incumbent 产物，而非只有 best_score 数字。
2. 冻结检查器版本、输入、随机种子和约束范围。
3. 从相同或明确可比的起点比较候选；记录难度或产物成熟度差异。
4. 保存样本数、聚合分数、波动量、实际耗时与可用成本数据。
5. 先满足地板与 horizon，再判断质量或成本的改进。
6. 未达到事先定义的实质差异、证据不足或方向冲突时，继续观察并保留 incumbent。
7. 候选失效时恢复所拥有的文件及关联证据，不覆盖用户原有修改。

对可生成随机实例的任务，使用配对实例/种子减少比较噪声；模型无法固定种子时记录重复 trial 身份，不虚构确定性。

### 8.3 最小观测记录

以下是逻辑字段，不要求立刻新增 JSON 依赖或全部扩展现有 rec 文件：

| 字段组 | 含义 |
|---|---|
| 身份 | run、尝试、策略版本、基线/候选产物摘要 |
| 测量条件 | AC、仪器摘要、输入/任务版本、seed 或 trial 身份 |
| 读数 | 样本数、聚合结果、波动量、缺失原因 |
| 成本 | 实际时长、可用的 tokens/费用、验证与恢复开销 |
| 资格 | 地板/horizon 是否通过、是否具有可比较性 |

声明 `sd/var` 的场景，需要把实际波动信息纳入证据后才能恢复推荐。不能用一个固定 tolerance 冒充置信区间。

### 8.4 验收

- 同一起点的候选比较不借用其他策略的收益。
- 单次偶然高分不能直接晋升通用策略。
- 分数更高但破坏约束的候选不能替代 incumbent。
- 噪声覆盖观察差异时不宣布显著获益。
- 恢复 best artifact 后可以独立复现其检查结果。

## 9. W7：形成可执行的策略晋升与撤回

### 9.1 三层循环

| 层级 | 可以自主改变什么 | 需要的证据 |
|---|---|---|
| 当前任务执行 | 修改产物、选择下一次局部尝试 | 当前契约下的检查与失败证据 |
| 当前任务策略 | 改变拆分、工具使用和局部打法 | 可比测量、明确适用条件与失效结果 |
| 可复用策略/skill | 产生、试验、晋升政策候选 | 冻结评估、留出任务收益、可撤回版本 |

验收器、用户成功定义和评分口径不属于优化 worker 可自由修改的内容。

### 9.2 策略记录

沿用现有 `.goal/proposals/` 作为候选入口，最少保存：触发证据、适用条件、相对现行版本的差异、支持/反对实验、撤回条件。历史失败和无收益结果同样保留。

建议状态：

```text
候选 → 本地复现 → 留出验证 → 启用 → 监测/撤回
```

- 一次胜利只产生候选；不能直接成为常驻通用规则。
- 换标签、换角色名称不能抹去失败历史；策略版本必须对应实际行为差异。
- 任务重复次数与晋升证据分开，现有 promote 提示只代表值得检查。
- 启用条件由事先授权的实验协议决定；授权范围内可自动试验和撤回。
- 涉及扩大权限、改变已批准契约或对外发布时，再按现有授权边界处理。

### 9.3 晋升验收

给候选提供本地获益但留出退化的数据，应保留 incumbent；提供符合事先收益条件且无约束回归的数据，才允许晋升。晋升后检测到退化，必须能恢复上一策略版本，并保留撤回原因。

## 10. W8：让 forge 的穷尽判断对应实际覆盖

“连续若干轮没有新发现”仅描述本轮探测过程，不能单独证明搜索空间已充分覆盖。

每次 critic/dry 证据至少关联实际探测维度、输入范围、执行结果、与既有探测的差异、仍未覆盖的部分。不要求为了凑数增加维度，也不奖励制造无价值 finding。

建议：

- 维持原有 floor、dry streak、completeness critic 的结构。
- 把 dry 条件绑定到实际探测与结果，而非只有 CLEAR 文本。
- 重复同一个探测可以验证稳定性，但不冒充新增覆盖。
- 预算不足以进一步验证时报告有界结论和剩余盲区；不能把预算耗尽包装为穷尽证明。
- 对可精确求解的小实例，用独立参考求解器校验质量；大实例继续报告可证明下界/上界或已知比较基线，适用时才采用。

验收包括：重复 CLEAR、固定探测遗漏缺陷、新输入触发缺陷、无新缺陷但确有新增覆盖，以及预算耗尽时的诚实收尾。

## 11. W9：把评估分成正确性、行为和效用

### 11.1 三套证据

| 层次 | 回答的问题 | 合适方法 |
|---|---|---|
| 实现正确性 | 脚本是否遵守约定语义 | 单元、端到端、故障注入、定向变异 |
| Agent 行为 | 实际执行者是否正确使用协议 | 全新上下文的真实任务试跑、工具轨迹检查 |
| 策略效用 | 是否比基线更值得使用 | 配对、多次、留出任务和消融 |

### 11.2 定向变异

在隔离副本中故意移除内容绑定、把错误读数变成零、关闭过期判断、提前写入拒绝请求等。对应测试必须失败；否则这些测试不足以保护该语义。

变异只发生在临时副本，报告变异点与被哪条测试捕获。不追求一个漂亮的全局变异分数，优先覆盖已经承诺的五条不变量。

### 11.3 首批实际任务

| 类型 | 主要观测 |
|---|---|
| 小型交付任务 | 规划、契约、验证开销是否合理 |
| 中型多模块任务 | 拆分、接口、join、并行净收益 |
| 有噪声的优化任务 | 测量重复、误推荐、最佳产物保持 |
| 中断恢复任务 | worker 故障、账本一致性、预算和成果保留 |

第一阶段：4 类任务各 3 次配对，普通流程与 goal-loop 共 24 次尝试。该规模用于发现大缺陷和估计开销，不保证足以证明统计优势。

如果要回答“是否强于宿主原生 `/goal`”，再以相同任务和口径增加原生 `/goal` 的 12 次尝试，总计 36 次，并记录宿主版本与真实调用路径。不能把普通提示词流程重命名为原生 `/goal`。

串行/并行、策略反馈开关等消融另外预注册预算；不要把它们默认包含在上面的样本数中。

### 11.4 实验纪律

- 冻结代码版本、模型设置、初始任务状态、验收器、预算与比较口径。
- 按任务分组随机或交替 AB/BA 顺序，避免所有 baseline 先跑带来的时序偏差。
- 记录资源容量与队列等待，不把并行独占更多计算资源当作免费加速。
- 相互隔离产物、上下文和策略经验；隐藏答案不进入 worker 简报。
- 根验收在独立环境运行；执行者同意不读验收文件与真正的权限隔离要明确区分。
- 原始失败先封存；看过失败后的同任务修复归入开发验证。
- 报告所有尝试，包括超时、取消、环境故障和无结果；预先约定环境故障如何分类，不能事后只删不利样本。
- 原始工具输出、产物补丁、运行配置、时间戳、评分结果足以复放；缺失信息写明。

## 12. Metrics：定义、分母与缺失值

指标采用顺序比较：有效交付率 → 预算内质量 → 同等质量下的成本。不要先合成一个可以通过牺牲正确性刷高的综合分。

| 指标 | 定义与口径 |
|---|---|
| 预算内有效交付率 | 截止前完成且通过独立验收的尝试数 / 全部尝试数 |
| 误接受率 | skill 发 GO 但独立验收失败的次数 / 发 GO 的次数；无 GO 时未定义 |
| 同预算质量 | 相同任务、时间和约束下的最终质量；未满足地板单独列示 |
| 每次有效交付成本 | 全部尝试总成本 / 有效交付数；零交付时未定义 |
| 交付时间 | 区分执行者声明、门控完成、独立验收完成三个时点；比较使用预注册的一种 |
| 成功随时间曲线 | 在各时间阈值前完成独立验收的比例，包含失败与超时 |
| 条件时间分布 | 若只对成功样本算 median/p90，明确标为成功条件下，不能代表总体 |
| 首次有效产出延迟 | 从 run/worker 派发到首次满足定义的可用结果；不是首条工具调用 |
| 协议开销 | 规划、契约、协调、收账、验收分别计时；并发区间不重复相加为墙钟 |
| 并行净收益 | 同等约束下的交付时间/成本变化，包含启动、join、返工和故障 |
| 恢复损失 | 故障后丢失的有效成果、重复工作及恢复耗时 |
| 策略晋升结果 | 候选、晋升、撤回数量及各自原始证据，不以晋升数量作为目标 |

失败是预算删失或明确失败事件，不可直接排除。整体完成率不足以识别 median/p90 时报告不可估计；不能把失败一律设成一个时间值再称为真实交付分位数。

可用 tokens/费用应包含 controller、worker、critic、测量准备、重试与失败开销。未暴露遥测的运行不得填零；基于价格换算的费用应注明计算口径与版本。

初期报告任务级配对差异及不确定性；缺少足够样本时只陈述观察，不宣布显著优势。

## 13. 实施顺序与每阶段交付

| 阶段 | 内容 | 依赖 | 必须交付 |
|---|---|---|---|
| A1 | W1 内容指纹 | 无 | Git/非 Git 反例、统一实现、旧证据迁移规则 |
| A2 | W2 完整预检 | 无，可与 A1 独立准备 | 拒绝操作不改变 ledger 的回归 |
| A3 | W2 提交恢复与单写者 | A2 | 提交点、幂等恢复、并发/崩溃注入测试 |
| A4 | W3 统一预算与取消 | A3 的所有权/恢复基础 | 总截止、超时传播、resume 测试 |
| B1 | W4 事件口径 | A3 | 实现/测量/声明/恢复的可区分统计 |
| B2 | W5 并行成本 | A4、B1 | 真实遥测及串行/并行选择依据 |
| C1 | W6 候选比较与最佳产物 | A1、A3、B1 | 可恢复 incumbent、可比测量、噪声场景 |
| C2 | W7 策略晋升 | C1 | 候选到撤回的真实成功与拒绝路径 |
| C3 | W8 forge 覆盖证据 | C1 | 探测记录与诚实穷尽/预算退出 |
| D | W9 能力与效用评估 | A 阶段先完成；其余按被测能力完成 | 配对任务、基线、原始结果、结论边界 |

按阶段输出可审查的小改动。能够独立修改的文件域可以分工；内容指纹与交易语义的接口必须先定，不能让多个 worker 同时改同一状态核心。

### 13.1 每个实现变更的完成定义

1. 反例先在旧实现失败，变更后通过。
2. 没有通过放宽契约、跳过失败或修改预期来制造成功。
3. 适用的原有回归通过；语义确需变化时记录旧断言为什么不再成立。
4. 原始输入、输出、版本、补丁和检查结果可独立复放。
5. 明确新增持久化状态及其恢复、迁移和撤回方式。
6. 常驻入口只保留会改变决策的必要说明；删除已被脚本可靠承担的重复步骤。

### 13.2 发布门槛

- A 阶段完成前，不把版本标为“核心可信性已完成”或“可严格无人值守”。
- 没有真实优化任务和留出验证前，不把局部分数反馈宣传为通用自主进化。
- 相同质量下的成本优势未被观察到之前，不宣传“更高效”。
- 是否获得更高工程评分取决于证据和缺陷关闭情况，不能把固定分数当成验收 AC。
